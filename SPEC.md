# SPEC: личный кабинет ученика (`apps/shop`)

Статус: черновик к утверждению. Всё, помеченное **[ТРЕБУЕТ УТВЕРЖДЕНИЯ]**, меняет
shared-пакет `@repo/db` и/или существующий код `apps/platform`. `@repo/ui` эта
работа **не меняет** — из него только потребляем (см. A7).

---

## 1. Цели

1. Ученик входит по логину и паролю на едином домене `shop.{rootDomain}` — без
   поддомена школы. Организация берётся из сессии.
2. Кабинет показывает: профиль (свои данные + родители), посещаемость, баланс
   астрокоинов с историей, историю заказов.
3. Магазин: каталог по категориям, карточка товара, корзина, оформление заказа за
   астрокоины.
4. Всё живёт в этом монорепо и переиспользует существующие БД (`@repo/db`) и
   дизайн-систему (`@repo/ui`). Ни одной копии Prisma-схемы, ни одного форка кнопки.

## 2. Не-цели (явно)

- **Ачивки.** В БД их нет ни в каком виде. В v1 — раздел-заглушка «Скоро». Ни
  таблиц, ни правил, ни выдачи.
- **Отзывы и рейтинги товаров.** Поля `Product.rating/reviews` остаются мёртвыми.
- **Смена пароля учеником.** Пароль выдаёт и перевыпускает школа (см. §6.4).
- **Самостоятельная отмена заказа учеником.** Статусами рулит staff в платформе.
- **Правка учеником своих данных.** Актуализация данных — существующий контур
  родителя (`/cabinet/{token}`), его не трогаем.
- **Уведомления школе о новом заказе** (smart-feed) — чужая фича, вне скоупа.
- **Кеширование.** Осознанно ноль: см. §5.
- **Регистрация/восстановление пароля.** Аккаунт создаёт только staff.
- **Мобильное приложение, оплата рублями, доставка.**

## 3. Размещение и маршрутизация

| Параметр | Значение                                                                                       |
| -------- | ---------------------------------------------------------------------------------------------- |
| Пакет    | `apps/shop`, имя `shop`, порт **3002**                                                         |
| Домен    | `shop.{rootDomain}`, резолвится DNS/реверс-прокси **напрямую** в этот деплой — как `apps/docs` |
| Локально | `http://localhost:3002`                                                                        |

`middleware`/`proxy` в `apps/shop` делает ровно два гейта (§7).

## 5. Кеширование и ревалидация

**Кеша нет. Все чтения идут в БД на каждый запрос.**

Обоснование: каталог, остатки и коины пишет **другое приложение** (`apps/platform`,
отдельный деплой). Его `revalidateTag` физически не достаёт до кеша шопа — общей
памяти нет. Любой кеш здесь означал бы webhook-контур между деплоями ради магазина
на десятки товаров.

Конкретно:

- каждая страница — `export const dynamic = 'force-dynamic'`;
- Prisma-клиент `@repo/db` — singleton, `fetch`-кеш Next не задействован;
- клиентские мутации (корзина, чекаут) — `useMutation` + `router.refresh()`;
  TanStack Query поверх server actions только там, где список действительно
  перерисовывается (корзина). Каталог и профиль — чистый RSC, без query-слоя.

Инвариант: **цена и остаток проверяются повторно внутри транзакции чекаута.** Даже
если бы UI показал устаревшие данные, покупка по старой цене невозможна.

## 6. Модель данных: что приложение **пишет**, а что только **читает**

### 6.1 Владеет (пишет)

| Таблица                          | Операции                                                       |
| -------------------------------- | -------------------------------------------------------------- |
| `Cart`, `CartItem`               | создание, изменение количества, удаление, очистка при чекауте  |
| `Order`, `OrderItem` **(новая)** | создание при чекауте (только `PENDING`)                        |
| `CoinTransaction` **(новая)**    | одна запись `ORDER_PURCHASE` на заказ                          |
| `StudentAccount.coins`           | `decrement` при чекауте — **только внутри транзакции чекаута** |
| `Product.quantity`               | `decrement` при чекауте — **только внутри транзакции чекаута** |
| `StudentSession` **(новая)**     | вход/выход                                                     |

### 6.2 Только читает

`Student`, `Parent`, `StudentParent`, `StudentGroup`, `Group`, `Course`,
`Attendance`, `Lesson`, `Product` (кроме `quantity`), `Category`, `Organization`,
`OrganizationFeature`, `StudentAccount` (кроме `coins`).

Ученик **не** видит и не читает: `Wallet`, `Payment`, `lessonsBalance`,
`Attendance.comment`, `Attendance.isWarned`, отработки, `Parent.accessToken`,
`Student.editToken`, всё из `finance.prisma`.

### 6.3 Мультитенантность

Организация ученика приходит **из сессии**, а не из поддомена (домен единый).
Резолвится один раз в middleware `studentAction`:

```
ctx = { student: { id, organizationId }, org: { id, slug, timezone }, disabledShop: boolean }
```

**Изоляция ручная, как в платформе.** Каждый запрос и каждая мутация обязаны
нести `organizationId: ctx.student.organizationId`. Дополнительно каждое чтение
чужой по своей природе сущности (`Product`, `Attendance`) фильтруется ещё и по
`studentId`. Правило для ревью: в `apps/shop` **нет ни одного** `prisma.*` вызова
без `organizationId` в `where`.

### 6.4 Пароли: hash + обратимая копия

Требование школы «менеджер видит пароль ученика всегда» и криптографический хеш
несовместимы by design. Компромисс:

- better-auth хранит свой хеш (по нему идёт вход);
- рядом `StudentAccount.passwordEnc Bytes` — AES-256-GCM, ключ `STUDENT_PW_KEY`
  в env (не в БД), формат `nonce || ciphertext || tag`;
- **ученик пароль не меняет** → две копии не могут разойтись by construction;
- пароль создаёт/перевыпускает только staff в платформе, обе копии пишутся в
  одной транзакции;
- показ пароля в карточке ученика — за permission-гейтом, факт показа логируется.

Колонка `StudentAccount.password String` (сейчас plaintext) **удаляется** после
миграции.

## 7. Гейты доступа

Реализуются в `apps/shop/src/proxy.ts` (Next 16) + повторно в `studentAction`
(fail-closed, middleware не считается защитой).

1. **Нет сессии** → редирект на `/login`. Кроме `/login`.
2. **Организация недоступна** (удалена / `Member`-связь пропала / орга
   заблокирована) → сессия аннулируется, редирект на `/login` с сообщением.
   Проверяется **на каждом запросе**, а не только при входе.
3. **Фича `shop` отключена у организации** → роуты `/shop*`, `/cart`, `/orders`
   отдают 404/редирект на `/`, пункты меню скрыты. Кабинет (профиль,
   посещаемость, коины) работает.
4. **Нет `StudentAccount`** → войти невозможно. Сам//регистрации нет.

Осознанно **не** гейтим: статус ученика (`StudentGroup.status = DISMISSED /
COMPLETED`). Отчисленный ученик пользуется кабинетом и магазином наравне со всеми,
пока школа не удалит аккаунт. Это решение продукта, а не недосмотр.

## 8. Server Actions

Все — `next-safe-action`, клиент `studentAction` (аналог `authAction` платформы):
инъекция `ctx`, `.metadata({ actionName })`, Zod на входе. Магазинные — через
`shopAction = studentAction.use(featureGate('shop'))`, чтобы серверный гейт нельзя
было забыть.

Раскладка по фичам: `apps/shop/src/features/{auth,profile,attendance,coins,catalog,cart,orders}/`
— `actions.ts` / `queries.ts` / `schemas.ts` / `components/`, как в платформе.

### Вход/выход

Через better-auth напрямую (`authClient.signIn.username` / `signOut`), не через
safe-action. Логин отправляется как есть (глобально уникален).

| Ошибка                | Сообщение                                                                              |
| --------------------- | -------------------------------------------------------------------------------------- |
| неверный логин/пароль | «Неверный логин или пароль» (одинаково для обоих — не раскрываем существование логина) |
| орга недоступна       | «Школа недоступна. Обратитесь к администратору»                                        |


### Каталог

```ts

  id, name, description: string | null, imageUrl: string, price: number,
  quantity: number, category: { id, name },
}>
// where: { organizationId, archivedAt: null }

getProduct: { id: number } -> Product | ошибка NOT_FOUND
// archivedAt != null → NOT_FOUND даже по прямой ссылке
```

### Корзина

```ts
getCart: void -> {
  items: Array<{ productId, name, imageUrl, price, quantity, available: number }>,
  total: number,
  coins: number,
  issues: CheckoutIssue[],   // предварительная валидация, см. ниже
}

addToCart: { productId: number, quantity: number >= 1 } -> void
  // upsert по @@unique([cartId, productId]); Cart создаётся лениво

setCartItemQuantity: { productId: number, quantity: number >= 1 } -> void
removeCartItem: { productId: number } -> void
clearCart: void -> void
```

### Чекаут — единственная нетривиальная операция

```ts
checkout: void -> { orderId: number } | ActionError { issues: CheckoutIssue[] }

type CheckoutIssue =
  | { productId: number, name: string, kind: 'OUT_OF_STOCK', available: number }
  | { productId: number, name: string, kind: 'PRICE_CHANGED', oldPrice: number, newPrice: number }
  | { productId: number, name: string, kind: 'UNAVAILABLE' }        // архивирован
  | { kind: 'INSUFFICIENT_COINS', needed: number, available: number }
```

Семантика — **всё-или-ничего**:

1. Одна `prisma.$transaction`.
2. Перечитать товары `FOR UPDATE`-семантикой (`updateMany` с условием на остаток —
   см. ниже), перечитать `coins`.
3. Собрать `issues`. Непусто → **rollback**, корзина не тронута, вернуть весь
   список проблем разом (не первую).
4. Иначе: списать `Product.quantity` условным апдейтом
   `updateMany({ where: { id, organizationId, quantity: { gte: qty } }, data: { quantity: { decrement: qty } } })`
   — если `count !== 1`, кто-то успел раньше → бросить и откатить.
5. Списать `StudentAccount.coins` тем же приёмом (`coins: { gte: total }`).
6. Создать `Order` (`PENDING`) + `OrderItem[]` c `priceAtPurchase`.
7. Записать `CoinTransaction { amount: -total, reason: ORDER_PURCHASE, orderId }`.
8. Очистить `CartItem` этого заказа.

Условные `updateMany` — вместо блокировок; это и есть защита от двух вкладок и от
гонки с правкой товара в платформе.

### Заказы

```ts
getOrders: void -> Array<{
  id, status: OrderStatus, createdAt: Date, total: number,
  items: Array<{ name, imageUrl, quantity, priceAtPurchase }>,
}>
```

Мутаций заказа у ученика нет.

## 11. Критерии приёмки

Сформулированы как утверждения, каждое проверяемо тестом. В репозитории тест-раннера
сегодня нет — проверка ручная либо первым же тестом, когда раннер появится.

### Вход и доступ

1. Вход с верным логином и паролем ставит куку `edu_student.*` и ведёт на `/`.
2. Вход с неверным паролем и вход с несуществующим логином возвращают **одинаковый**
   текст ошибки и не создают сессию.
3. Запрос любой страницы, кроме `/login`, без куки отдаёт редирект на `/login`.
4. У ученика, чья организация удалена, существующая кука не даёт доступа: следующий
   же запрос ведёт на `/login`.
5. При `OrganizationFeature('shop') = disabled` запрос `/shop`, `/cart`, `/orders`
   не отдаёт 200, а `/`, `/attendance`, `/coins` отдают 200.
6. `POST` на `addToCart` при отключённой фиче возвращает ошибку, даже если
   middleware обойдён (гейт продублирован в `shopAction`).
7. Ученик со статусом `DISMISSED` во всех группах входит и успешно оформляет заказ.

### Изоляция

8. Ни один вызов `prisma.*` в `apps/shop` не выполняется без `organizationId` в
   `where` (проверяется grep'ом по диффу в ревью).
9. `getProduct({ id })` для товара чужой организации возвращает NOT_FOUND, а не товар.
10. Ответ `getProfile` не содержит подстроки `accessToken`, `editToken` ни на одном
    уровне вложенности.
11. Ответ `getAttendance` не содержит полей `comment`, `isWarned`, `walletId`.

### Каталог

12. Товар с `archivedAt != null` отсутствует в `getCatalog` и даёт NOT_FOUND в
    `getProduct` по прямой ссылке.
13. Изменение цены товара в платформе видно на `/shop` при следующем же запросе,
    без ожидания и без ручного сброса кеша.

### Корзина и чекаут

14. `addToCart` дважды по одному товару даёт одну строку `CartItem` с суммарным
    количеством (уникальность `[cartId, productId]` не нарушается).
15. Чекаут корзины на сумму больше баланса: заказ не создан, `Product.quantity` и
    `StudentAccount.coins` не изменились, ответ содержит `INSUFFICIENT_COINS` с
    фактическими числами.
16. Чекаут, когда один из трёх товаров кончился: заказ не создан, **все три**
    позиции остались в корзине, ответ содержит ровно один `OUT_OF_STOCK` с именем
    этого товара.
17. Чекаут, когда цена товара выросла между открытием корзины и подтверждением:
    заказ не создан, ответ содержит `PRICE_CHANGED` со старой и новой ценой.
18. Успешный чекаут в одной транзакции: создан `Order(PENDING)` + N `OrderItem` с
    `priceAtPurchase`, `coins` уменьшился ровно на сумму, `Product.quantity`
    каждого товара уменьшился ровно на заказанное, `CartItem` пусты, создана одна
    `CoinTransaction(ORDER_PURCHASE, -total)`.
19. Два одновременных чекаута последней единицы товара: ровно один успевает, второй
    получает `OUT_OF_STOCK`, `Product.quantity` не уходит ниже нуля.
20. Баланс коинов никогда не отрицателен ни при какой последовательности операций.

### Заказы и коины

21. `Order.status`, изменённый staff в платформе, виден ученику в `/orders` при
    следующем запросе.
22. Отмена заказа в платформе возвращает коины и остаток и пишет
    `CoinTransaction(ORDER_CANCELLED, +total)`; баланс сходится с суммой леджера.
23. Архивация товара в платформе не удаляет ни одного `Order`/`OrderItem`; товар
    продолжает отображаться в истории заказов ученика.
24. Сумма `CoinTransaction.amount` по ученику равна `StudentAccount.coins` (после
    строки `INITIAL_BALANCE`) — инвариант леджера.
25. Отметка `PRESENT` в платформе создаёт `CoinTransaction(ATTENDANCE_PRESENT, +10)`,
    снятие отметки — компенсирующую строку; счётчик и леджер остаются согласованы.

### Пароли и логины

26. Создание второго `StudentAccount` с существующим логином (в любой другой школе)
    отклоняется с сообщением «Логин занят».
27. Расшифровка `passwordEnc` даёт тот же пароль, которым ученик успешно входит.
28. При отсутствующем/неверном `STUDENT_PW_KEY` показ пароля в платформе даёт
    внятную ошибку, а вход ученика при этом продолжает работать (вход идёт по хешу).
29. В БД после миграции нет колонки `StudentAccount.password`.

### Совместимость платформы

30. `pnpm check` проходит на всём монорепо после миграции S1–S5.
31. Страницы `/{slug}/shop/products`, `/categories`, `/orders` в платформе
    открываются и корректно отображают мигрированные заказы (шапка + позиции).

## 12. Сквозной сценарий верификации

Один проход, руками, на локальном стенде (`platform:3000`, `shop:3002`, общая БД):

1. **Платформа:** создать категорию «Канцелярия» и товар «Ручка», цена 30, остаток 2,
   картинка загружена.
2. **Платформа:** у ученика Иванова создать аккаунт — логин `ivanov`, пароль
   автогенерируется; убедиться, что пароль виден в карточке.
3. **Платформа:** попытаться создать аккаунт с логином `ivanov` другому ученику →
   «Логин занят».
4. **Платформа:** отметить Иванова `PRESENT` на уроке → баланс стал 10; в карточке
   начислить вручную ещё 50 → баланс 60.
5. **Шоп:** войти как `ivanov` с показанным паролем.
6. **Шоп `/`:** профиль показывает ФИО, группу с курсом, родителя с телефоном.
   Никаких ссылок с токенами на странице нет (проверить HTML).
7. **Шоп `/attendance`:** есть строка с датой урока и статусом «Был». Комментария
   учителя в HTML нет.
8. **Шоп `/coins`:** баланс 60, две строки — «Посещение +10» и «Начисление +50».
9. **Шоп `/shop`:** «Ручка» видна, цена 30, остаток 2. Добавить 2 шт. в корзину.
10. **Шоп `/cart`:** итог 60, кнопка активна. **Не подтверждать.**
11. **Платформа (вторая вкладка):** изменить остаток «Ручки» на 1.
12. **Шоп:** подтвердить заказ → заказ не создан, показано «Осталось только 1 шт.»,
    обе единицы остались в корзине, баланс всё ещё 60.
13. **Шоп:** уменьшить количество до 1, подтвердить → заказ создан, статус
    «В обработке», баланс 30, в `/coins` появилась строка «Покупка −30».
14. **Платформа:** остаток «Ручки» стал 0; заказ виден в `/shop/orders` одной шапкой
    с одной позицией и ценой 30.
15. **Платформа:** отменить заказ → баланс ученика 60, остаток «Ручки» 1.
16. **Шоп:** в `/orders` статус «Отменён», в `/coins` строка «Возврат +30», баланс 60.
17. **Платформа:** архивировать «Ручку» → в `/shop` шопа её нет, прямая ссылка
    `/shop/{id}` даёт 404, но в `/orders` заказ с «Ручкой» на месте.
18. **Платформа:** отключить фичу «Магазин» → в шопе `/shop`, `/cart`, `/orders`
    недоступны, пункты меню исчезли, `/`, `/attendance`, `/coins` работают.
19. **Шоп:** выйти → любая страница ведёт на `/login`.

Проход считается успешным, только если пункты 12, 15, 17 и 18 отработали ровно
как описано — это четыре места, где текущая схема и текущий код ломались бы.

## 13. Открытые допущения (не блокируют, зафиксировать)

1. Награда за посещение остаётся хардкодом `+10` в платформе; настройки размера
   награды в v1 нет.
2. `Order` не хранит снапшот названия/картинки товара — целостность истории
   обеспечивает `archivedAt` + `Restrict` (S2). Если позже понадобится физическое
   удаление товаров, снапшот придётся добавить.
3. Пагинации нет нигде: каталог, посещаемость (100 записей), коины (50), заказы —
   плоские списки. Порог пересматривается, когда у школы появится >200 товаров.
4. `@repo/config` (общие eslint/ts/tailwind-конфиги) по-прежнему не заводится:
   `apps/shop` копирует конфиги `apps/docs`. Третий потребитель — повод вернуться.
