# Перевод боевой базы на новую денежную модель

Инструкция проверена целиком на копии боевой базы 10.08.2026: дамп прода развёрнут
локально, все шаги прогнаны в этом порядке, все сверки зелёные.

**Исходное состояние прода:** последняя применённая миграция
`20260721120000_group_name`, впереди 15 миграций. В базе 884 ученика, 1 270 кошельков,
2 268 оплат, 34 874 посещения, 856 учётных записей учеников с открытыми паролями.

Три шага необратимы: перенос паролей, разметка истории и закрытие долгов.
**Бэкап обязателен.**

---

## Перед началом

**Бэкап базы.**

```bash
pg_dump "$DATABASE_URL" -Fc -f alg-before-money-migration.dump
```

**Проверить `apps/platform/.env` на сервере.** Скрипты читают именно его.

- `DATABASE_URL` — боевая база.
- `STUDENT_PW_KEY` — 32 байта в base64. **Самое опасное место всей миграции.** Этим
  ключом шифруются пароли учеников, и он должен остаться тем же навсегда: сменишь или
  потеряешь — школа больше не сможет показать ученику его пароль, а восстановить будет
  неоткуда, потому что открытые пароли к тому времени уже удалены. Если ключа ещё нет,
  сгенерируй один раз и положи в хранилище секретов:
  `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`

**Развернуть монорепо и клиент.**

```bash
pnpm install --frozen-lockfile
pnpm --filter @repo/db generate
```

**Окно обслуживания.** Шаги 2–9 переписывают деньги по всей истории. Приложение на это
время лучше погасить: если в середине кто-то проведёт оплату или отметит посещение,
разметка ляжет поверх, и сверка это покажет, но разбираться придётся руками.

---

## Порядок

### 1. Убедиться, что незавершённых миграций нет

```bash
pnpm --filter @repo/db exec prisma migrate status
```

Ожидаемо: список из 15 непримененных. Записи со старыми падениями, помеченные
откаченными, деплою не мешают — на копии прода их было четыре, майских.

### 2. Накатить миграции — первый заход **упадёт, и это правильно**

```bash
pnpm --filter @repo/db exec prisma migrate deploy
```

Дойдёт до `20260723120100_drop_student_password` и остановится:

```
Database error: ERROR: backfill-student-auth не отработал:
есть StudentAccount без passwordEnc/studentUserId
```

Это защита в самой миграции: между созданием таблиц better-auth и удалением колонки с
открытым паролем обязан отработать перенос, а посчитать хеш в SQL нельзя. Падение
происходит в транзакции — база остаётся целой, пароли на месте.

### 3. Перенести пароли учеников

```bash
pnpm --filter platform exec tsx scripts/backfill-student-auth.ts
```

Ожидаемо: `перенесено аккаунтов — 856`. Скрипт для каждой записи проверяет, что шифр
расшифровывается обратно в исходный пароль, и падает на первой же несостыковке — если
`STUDENT_PW_KEY` не тот, узнаешь здесь, а не после удаления колонки.

### 4. Разрешить продолжение и доехать до конца

```bash
pnpm --filter @repo/db exec prisma migrate resolve --rolled-back 20260723120100_drop_student_password
pnpm --filter @repo/db exec prisma migrate deploy
```

Ожидаемо: `All migrations have been successfully applied.`

```bash
pnpm --filter @repo/db exec prisma migrate status   # Database schema is up to date!
pnpm --filter @repo/db generate
```

### 5. Починить оплаты с перепутанными полями

```bash
pnpm --filter platform exec tsx scripts/fix-swapped-payments.ts          # посмотреть
pnpm --filter platform exec tsx scripts/fix-swapped-payments.ts --apply  # записать
```

Четыре записи вида «4 ₽ за 5390 занятий» — при заведении поменяли местами сумму и
количество. Одна такая строка отдаёт тысячи фиктивных уроков остатка и делает сотню
занятий бесплатными, поэтому чинить надо **до** разметки. Скрипт печатает исходные
значения в JSON — сохрани вывод, это откат.

### 6. Разметить историю по пакетам

```bash
pnpm --filter platform exec tsx scripts/backfill-payment-packets.ts          # сводка
pnpm --filter platform exec tsx scripts/backfill-payment-packets.ts --apply  # записать
```

Проставляет каждому посещению цену **на дату визита** и раздаёт остатки пакетам.
Раздача детерминирована: повторный прогон по тем же данным даёт тот же результат.

Числа на копии прода: 34 493 проводки, из них 8 232 с пакетом и 9 862 «в долг» по
последней известной цене (456 из них без цены — у кошелька не было ни одной оплаты);
203 посещения без кошелька остались неразмеченными; 713 доплатформенных оплат привязаны
к кошелькам, у 313 кошелёк выбран догадкой — их список печатает `--verbose`, и школа
может поправить руками.

### 7. Открыть журнал движений

```bash
pnpm --filter platform exec tsx scripts/backfill-wallet-ledger.ts          # сводка
pnpm --filter platform exec tsx scripts/backfill-wallet-ledger.ts --apply  # записать
```

**Строго после шага 6** — журнал строится из проставленных проводок и остатков.
Повторно не запустится: увидит непустой журнал и откажется.

Числа на копии прода: 21 289 строк — 2 537 приходов, 18 094 списания, 658 строк сальдо.

### 8. Выкатить приложение

Новый код обязан оказаться на бою **до** следующего шага. Иначе старая логика продолжит
уводить балансы в минус, и закрытые долги наберутся заново.

### 9. Закрыть долги, оставшиеся от старой модели

```bash
pnpm --filter platform exec tsx scripts/close-negative-balances.ts          # посмотреть
pnpm --filter platform exec tsx scripts/close-negative-balances.ts --apply  # записать
```

Кошелькам с отрицательным балансом пишется корректировка в журнал, баланс становится
нулём. Строки посещаемости не трогаются: те уроки уже оценены и уже посчитаны в выручке
прошлых месяцев, а долг в рублях остаётся виден в отчёте «Авансы».

На копии прода: 124 кошелька на 265 уроков.

### 10. Сверки

```bash
pnpm --filter platform exec tsx scripts/check-ledger-core.ts      # ядро, транзакция откатывается
pnpm --filter platform exec tsx scripts/check-money-cases.ts      # 32 сценария
pnpm --filter platform exec tsx scripts/check-ledger.ts           # журнал против колонок
pnpm --filter platform exec tsx scripts/check-wallet-balance.ts   # баланс против пакетов
pnpm --filter platform exec tsx scripts/check-revenue-parity.ts   # отчёт против базы
```

Все читают базу и ничего не меняют. Первые две создают временные данные внутри
транзакции, которая в конце откатывается.

---

## Что красное и когда

Сверки завязаны на конечное состояние, поэтому в середине они законно падают.
Не пугаться:

| После шага | `check-wallet-balance` | `check-ledger` |
|---|---|---|
| 6 — разметка | красный: 124 кошелька в минусе | журнала ещё нет |
| 7 — журнал | красный: те же 124 | красный: «кошельков с отрицательным балансом: 124» |
| 9 — закрытие долгов | зелёный | зелёный |

---

## Чего делать нельзя

**Менять местами шаги 6 и 7.** Журнал строится из проводок; на пустой разметке он
запишет нули и разойдётся с колонками.

**Запускать шаг 9 до выкатки кода.** Долг, набежавший между правкой базы и деплоем,
обнулится вместе со старым, и его никто не соберёт.

**Терять или менять `STUDENT_PW_KEY`.** Ротации нет: пароли зашифрованы одним ключом,
открытых копий после шага 4 не остаётся.

**Считать падение на шаге 2 аварией.** Это единственный способ, которым Prisma даёт
вклиниться между двумя миграциями.

---

## Если пошло не так

**До шага 6** — откат из бэкапа, потерь нет.

**После шага 6** — восстанавливать из бэкапа целиком. Разметка переписывает 34 тысячи
строк, и точечно её не отменить.

**Разметка легла криво у отдельных кошельков** — это не повод откатывать всё: сверки
покажут, где именно, а список кошельков с выбором «по догадке» есть в выводе шага 6 с
`--verbose`. Поправить оплату и перезапустить разметку можно: она детерминирована.

**Пароли не расшифровываются после переезда** — значит `STUDENT_PW_KEY` не тот, которым
шифровали. Восстанавливать из бэкапа, снятого до шага 3, и повторять с правильным ключом.

---

## После миграции

Проверить руками на бою:

- у ученика с пустым кошельком отметить занятие → баланс остался нулём, в карточке
  появилась секция «Ждут оплаты»;
- провести этому ученику оплату → занятие получило её цену и ушло из списка;
- отменить эту оплату → снялось только непотраченное, отходенные занятия остались
  оплаченными.

Отчёт «Выручка» за прошлые месяцы должен совпасть с тем, что показывает
`check-revenue-parity`. На копии прода: Алгоритмика 17 358 192 ₽, А Класс 2 248 602 ₽ —
за весь период с сентября 2025 по август 2026.
